# On-device hand cues

Gesture input is optional. Offer and Accept buttons use the same server commands and remain available throughout. MediaPipe locates hand landmarks; PORTAL STAGE applies its own deliberate intent gate. It does not recognize a physical umbrella, infer whether one is open, identify a person, segment a body, or validate real-world occlusion.

Ordinary rehearsal has **Camera & hand cues**. Its native camera controller requests video only after explicit local consent. It shares the framing, cue region, dwell and button path below, but neither joins LiveKit nor uploads camera/anchor data. The local picture replaces only A in that browser; illustrated B stays clearly labeled. Stop, consent withdrawal, End and departure stop capture; cancellation also stops a late permission grant. This differs from the explicitly labeled loopback synthetic transport test and from real solo/duet media publication. The owner's recorded physical checks are described below; a dedicated production Chrome network-isolation audit remains a separate acceptance task.

`useGestureInput(video, options)` lives in `src/vision/use-gesture-input.ts`. Only its explicit `enable()` action starts the worker and loads assets. It consumes an existing private camera preview and never requests a camera itself. `disable()` and unmount terminate the worker and timers. Unsupported workers, failed assets, slow inference, an inactive tab, or a missing feed fall back to buttons with visible status.

A successful inference with no eligible selected hand reports “Tracking active — no selected hand detected,” rather than a runtime pause. This is expected for the synthetic transport plate and does not establish a successful human cue. Weak signal and a calibrated-hand mismatch show separate lighting/framing or hand-selection guidance. Worker, decoder and inference-age failures retain their distinct fallback messages; all paths keep button parity.

The bundled `@mediapipe/tasks-vision` 1.2.0 runtime, SIMD/non-SIMD WebAssembly, and fixed `hand_landmarker/float16/1` model are served from `/vision`. No runtime CDN is required. Frames are resized to at most 640 px on their longest edge and processed at a maximum of approximately 10 inferences per second with only one frame in flight. The worker closes each transferred bitmap; detection data is transient. There is no recording, raw-frame upload, landmark persistence, identity template, or local-storage calibration in this implementation. Semantic Offer/Accept requests use the show's normal action API. Each eligible inference refreshes a director-local presentation point, independently of the throttled `media.sendAnchor` path. Live peer positions still use the private LiveKit room's bounded, disposable messages and expiring calibration fallback. They do not write a whole show document for each movement.

The upstream SDK includes an aggregate usage-metrics sender. This isolated worker permits only same-origin fetch/XHR and blocks its external endpoint. That implemented worker guard provides the network restriction; the app currently has security headers and no configured Content Security Policy. Model input stays local; LiveKit transport of a performer camera is a separate, explicitly enabled media action.

## Calibration and intent

Confirm framing, the intended hand, and the cue region before assigning a `GestureCalibration`. All rectangles and points are normalized to 0–1. `apertureCalibration({slot,handedness,videoWidth,videoHeight})` derives the actual centered cover crop from the video's intrinsic dimensions and the shared 650 × 562 aperture. It returns null until dimensions are known; manual marker placement and durable calibration remain available without a camera. `cameraToStage()` rejects cropped-out, unsafe and nonfinite points, maps them once to visible aperture coordinates, and smooths a stable anchor with an 0.018 dead zone. A lost hand cancels dwell. The engine distinguishes a fresh selected hand from its internally retained point. A still hand refreshes the local presentation on every valid inference; a lost or weak hand retains the last local point for 1500 ms, then falls back to the calibration marker. Remote anchor expiry remains 1500 ms and its ownership/identity gates are unchanged.

Program uses an unmirrored camera. The private preview uses the same 650:562 aspect and centered cover crop, followed by a CSS mirror. New aperture calibrations therefore use `mirrored:false` for raw landmarks. The manual preview marker is already in visible aperture coordinates: invert its x coordinate once to save the unmirrored Program position. `rawRectToMirroredAperture()` applies the crop and inverse mirror to draw a raw cue region in that preview. Confirm direction visually on each actual camera, especially virtual cameras that may already flip pixels.

Handedness is normalized once by `subjectHandedness()`. The [current Tasks Web guide](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/web_js#handle_and_display_results) describes the subject's own left/right hands; horizontally mirrored **input pixels** invert that result. The Tasks graph [changed its labels in 0.10.5](https://github.com/google-ai-edge/mediapipe/commit/ed0c8d8d8bbd466eac1e483ab62a42dd7d486e96), so legacy Hands' selfie-input assumption does not apply to the shipped 1.2.0 Tasks runtime. The worker receives unmirrored pixels, and its labels are preserved. A CSS mirror of the preview does not flip handedness. New A setup defaults to Left hand, the portal side; B defaults to Right. Saved confirmed choices and both selectors remain available. The owner's physical left hand matched the raw Left label in the local diagnostic and subsequent recordings. Other cameras, virtual-camera mirror settings and B/right-hand use still need physical confirmation.

The supported visible grip region is x=0.16–0.84, y=0.30–0.72. Calibration takes the corresponding subsection of the intrinsic camera crop and maps it to that same visible region; it does not stretch the full video or full crop into a smaller safe rectangle. Cue regions are x=0.66–0.82 for A or x=0.18–0.34 for B, y=0.32–0.70, in visible Program coordinates. These are converted back to raw camera rectangles for detection and back to visible coordinates for cue inset/drift gates. A changed intrinsic aspect pauses gesture cues and position output until a fresh calibration confirmation; a same-aspect resolution change keeps the mapping valid. The older `defaultCalibration()` remains a legacy helper rather than the camera-geometry setup path.

Automated pixel-space geometry checks verify this transform for wide, portrait/narrow, square and matching-aspect inputs. Physical evidence is limited to the owner's camera recordings described below. Alignment across other people, cameras, framing, lighting and motion remains pending.

Each cue requires all of these conditions:

- Explicitly armed input and a confirmed valid region.
- The chosen hand, finite in-frame landmarks, and handedness classification score at least 0.8. The model's detection, hand-presence, and tracking thresholds are also 0.8. The visible score is **not** a calibrated probability of intent or measured gesture accuracy. This xyz-only hand model does not output per-landmark visibility: the SDK [fills that absent field with zero](https://github.com/google-ai-edge/mediapipe/blob/76f1d78eb1c350f882536adfa84d248ad0c84a60/mediapipe/tasks/web/components/processors/landmark_result.ts#L29-L34), so the HandLandmarker adapter does not use it as confidence.
- A geometrically open palm inside the inset cue region with bounded drift. The engine requires a neutral/lowered hand after arming or an offer change, avoiding acceptance from a hand already raised for an earlier cue.
- Continuous dwell of 900 ms to Offer or 1100 ms to Accept. A frame gap over 240 ms, lost signal, or an out-of-region hand cancels progress. A result over 400 ms old cannot trigger a cue.
- For Offer, the performer owns the prop and is eligible to offer. For Accept, the performer is the expected receiver of a current offer ID. A new offer cannot inherit the old offer's dwell.
- A 1800 ms cooldown and one request per eligibility/arming cycle. The server still checks ownership, version, epoch, consent, admission, and expiry before committing anything.

Two ambiguous detections of the selected hand are rejected. These conservative gates may miss intentional gestures. Re-arm or use the matching button; a failed network command is not treated as a successful transfer. Framing confirmation is a user-defined geometric setup, not a measured guarantee of hand-to-prop alignment.

## Local hand presentation

The director's local palm sample is fenced to the current show and epoch. It updates while the selected, armed hand owns the prop or is the receiver of a current offer. Receiver sampling is presentation only: `activeAnchorSlot`, network publishing permissions, server ownership and commit order are unchanged. On acceptance, the crossing targets the latest local palm and ends exactly at that target; no tracked hand means the calibrated fallback. While the performer holds an offered prop, the grip stays at the palm instead of taking the illustrated offer's forward offset.

Held umbrella and parcel positions use frame-rate-independent exponential smoothing with a 100 ms time constant. Crossings and the shelter beat bypass it. Mount, epoch change, hold/curtain and recovery snap to the current target. Reduced motion uses direct held positions. After tracking loss, the local grace expires before the held prop glides back to its fallback. The local camera rehearsal's manually placed marker remains separate from the temporary tracked point.

A thin gold ring fills clockwise during an armed, tracked dwell in the director's stage, flashes for 240 ms when a request fires, and shows a small lower-hand hint when another cue needs release. The flash means a request was made, not that the server accepted it. Feedback disappears on disarm, hold, tracking loss or an inference gap over 240 ms; retaining a prop through the loss grace cannot retain a stale dwell ring. Reduced motion keeps a static ring and suppresses the flash.

The single canonical renderer copies its clean stage frame for Program and the guest return before drawing this local feedback. Capturing the director's visible canvas includes the ring; published Program pixels do not. Live solo Program already receives the composed director video, including the prop position, rather than reconstructing it from anchor messages. No extra solo anchor-publishing path was added. An ordinary rehearsal's separate Program preview remains illustrated and uses the calibrated scene positions.

## Observed and pending verification

The first owner camera rehearsal on 3 November 2026 failed its hand-follow check: the closed left fist was raised but the umbrella remained at its marker. A subsequent eight-second local diagnostic sampled 24 frames, detecting the selected Left hand in 17 with handedness scores 0.9613–0.9793 and 21 landmarks. Every detected point's visibility field was zero, making the previous adapter's combined confidence zero. The shipped model has 21 × xyz outputs, with separate hand-presence and handedness scalars; it has no per-point visibility output. The adapter fix uses the bounded handedness score while preserving the 0.8 gates and all geometry, arming, release and dwell checks. Regression fixtures use the SDK's zero-visibility result shape and cover closed-fist tracking without cues, deliberate open-palm offer/accept, weak scores and malformed/ambiguous inputs.

A second follow recording still ran the old JavaScript adapter after deployment. Inspection of the actual loaded bundle confirmed the stale visibility gate; a cache-bypassing reload and bundle check established the corrected code before further physical checks. Both initial failed follow attempts remain failed observations.

Subsequent owner-consented recordings on runtime `cda6c18` show closed-fist follow, a ten-second still-hand hold, the gold dwell ring and release hint, and continued hand-follow after a catch. Three offers were recorded with physical gestures: one rehearsal offer and two live solo offers. Two return catches were recorded with physical gestures: one rehearsal catch and one live solo catch. The live solo audience choices used real, agent-typed messages from the owner's account, with one counted ballot per selected window; the director still closed voting and brought results onto the stage.

Full-resolution review of the final live catch places the grip roughly 10–15 canvas pixels from the visually estimated palm center in a 1920 × 1080 frame. The receiving pose remains steady after landing and follows the subsequent lift. This is a manual visual estimate from one owner and camera, with several pixels of uncertainty; it is not a general accuracy bound or a measured success rate. Camera and canonical-canvas recording operated together in these sessions. Private consent records, recordings and detailed QA remain outside Git.

Automated tests compare the shared crop transform with independent pixel-space CSS-cover math, including 16:9 and portrait/narrow sources, safe-region edges, mirrored overlays, narrow preview widths, manual-marker parity, aspect changes and identical visible cue thresholds. Gesture tests cover dead zones, disarmed input, wrong ownership/receiver, current offer IDs, continuous dwell, confidence and handedness loss, stale frames, replacement offers, ambiguous hands, held-palm repeat prevention, and bundled asset integrity. The revision-009 release adds a simulated ten-second still-hand hold, tracking-loss grace and glide, identical convergence at 30/60/144 fps, recovery snaps, live return targeting, current Tasks handedness, default hand selections, feedback freshness/reduced motion and clean capture-before-overlay checks. The confidence fix adds SDK-shaped zero-visibility regressions. Disposable-position tests still cover immutable peer metadata/identity, show/epoch, bounds, age/order/rate/size, backpressure, reset and fallback. These automated cases use synthetic observations and SDK mocks. The release passed 537 ordinary tests, with seven opt-in Neon checks skipped, plus typecheck, formatting and the optimized build.

Worker initialization and physical cues were observed on the owner's camera; camera-to-landmark latency was not instrumented. Intent success and false-activation rates remain pending trials with consenting people across varied skin tones, lighting, sleeves, occlusion, portrait/landscape cameras, one/two hands, seated positions, mobility needs, and CPU load. Multi-person, separate-device/network and OBS trials remain pending. Every trial must retain button parity. Do not quote the plan's accuracy or latency targets as measured outcomes.
